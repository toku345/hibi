小さなCLIの、設計をひもとく

入力から保存まで、
4つの役割で読み解く。

hibi は、仕事終わりの4問に答えて、その日の記録を残す OCaml 製のCLIです。
「どこが何を担当し、どうつながるか」を、コードの関係と実行時の流れに分けて見ていきます。

01

全体像とコンポーネント

処理を進めるのは Main。入力・データ・保存を、それぞれの部品へ依頼します。

コードの依存関係
誰が、誰を使うか部品を選ぶと、下に詳しい説明を表示
A → B は「A が B を呼び出す・参照する」狭い画面では図を横にスクロールできます
端末・パイプMain が質問を表示し、Input が回答を読む
環境変数Storage が HIBI_LOG_DIR / HOME を参照
ファイルシステムStorage がディレクトリとJSONを作成

各部品を、もう少し詳しく

見出しを押して開閉
Main質問と処理の進行bin/main.ml

プログラムの入口です。開始日時を取得し、4問を順番に表示します。Input から返った1行を Record で検証し、エラーなら同じ質問を繰り返します。

4問後に Record.create を呼び、全問未回答なら保存せず終了します。保存可能な Record.t が生成された場合だけ Storage に渡し、失敗や中断を終了コードへつなぎます。

読むときの入口
runcollect_recordaskstarted_at
関連する部品・ライブラリ

Input / Record / Storage
Ptime_clock：現在時刻とローカル時差を取得。

保存先の表示処理もここで定義し、Storage にコールバックとして渡します。

Input端末・パイプからの入力bin/input.ml / .mli

read_line () が、Enterで確定した1行を Main に返します。回答内容が妥当かどうかは判定しません。

標準入力が端末なら行編集、端末でなければパイプ入力を使います。端末入力で標準出力だけをリダイレクトする操作は拒否します。

Ctrl+D・EOFは End_of_file、Ctrl+Cは Sys.Break として通知します。端末の編集処理とシグナルハンドラーの後始末もこの部品が担います。

公開インターフェース
read_line : unit → string
内部の処理
read_terminalread_pipe

Lambda-Term：端末と行編集。
Lwt：端末処理と中断の扱い。
React（OCaml）：プロンプトのシグナル。
Zed：日本語を含む文字列と編集。

Record回答データと検証lib/record.ml / .mli

Record.t は「検証済みで、回答が1つ以上ある記録」を表す private record です。フィールドは読めますが、外部から直接生成・レコード更新はできません。

create が開始時刻（Ptime.t）・時差・4つの回答を検証します。スコアは1〜5、不正なUTF-8はエラーです。全問未回答なら記録を生成しません。JSON変換もこの部品が担います。端末への表示や保存は行いません。

空白だけかの判定には前後の空白を除いた値を使いますが、自由記述の回答は元の文字列を保持します。

公開インターフェース
type t = private { … }createtimestampscore_of_linetext_of_lineto_json

Ptime：日時をRFC 3339形式にする。
Yojson：JSONのデータ構造を表す。

Main と Storage の両方から使われます。

StorageJSONファイルの保存lib/storage.ml / .mli

環境変数から保存先を選び、必要なディレクトリを作り、JSONを新しいファイルへ保存します。Record の to_json を呼び、Yojson で文字列にします。

保存先がGitリポジトリ内なら拒否。ファイルは排他的に新規作成し、同名なら連番を進めます。既存の記録を上書きしません。

ファイルを書き終えた後、渡された report 関数を呼びます。報告完了前に保存・報告が失敗した場合や中断された場合は、今回のファイルの削除を試み、削除失敗もエラーに含めます。

公開インターフェース
log_directorysave ~dir record ~report
内部の処理
prepare_directoryoutside_gitwith_sigint_blocked

Unix：パス・権限・ファイル・シグナル。
Yojson：JSONを文字列にする。

新規ディレクトリは0700、ファイルは0600で作成します。既存ディレクトリの権限は変更しません。

型とテストの役割：private record が「検証を通さずに Record.t を作る・更新する」操作を禁止します。生成関数の実装が正しく検証・変換するかは、具体例とプロパティベーステストで確かめます。検証済みのデータをそのまま読み取れる形を保ちます。

図の読み方：コンポーネントは「ひとまとまりの役割を持つ部品」です。ここではOCamlのモジュールに対応します。bin/ の Main・Input は実行ファイルに、lib/ の Record・Storage は Hibi ライブラリに含まれます。4つとも同じプロセス内で動きます。

02

入力から保存まで

こちらの図は、上から下が実行順です。質問の進行は Main が制御します。

実行時の流れ
  1. 01

    質問開始時の日時を決める

    Main → Record

    Ptime_clock で現在時刻と時差を取得し、Record.timestamp で表現可能かを確認します。開始時刻と時差を保持し、生成時にも検証します。

  2. 02

    質問を表示し、1行ずつ検証する

    Main

    Main.ask → Input.read_line → Main に1行を返す → Record で検証。この繰り返しで4問に答えます。

    不正な入力なら同じ質問を再表示。Ctrl+C・Ctrl+D・EOFなら、回答を保存せず終了します。

  3. 03

    全項目を検証して記録を生成する

    Main → Record

    Record.create に開始時刻・時差・4つの回答を渡します。空白だけの回答を未回答にし、妥当で1問以上回答があれば Record.t を生成します。

  4. 04

    生成結果に応じて分岐する

    Main

    Ok (Some record) は保存へ、Ok None は未回答として正常終了、Error reason はエラーとして終了します。

    全問未回答なら、この段階で正常終了。保存先の取得やファイル作成へは進みません。

  5. 05

    保存先を選ぶ

    Main → Storage

    Storage.log_directory が HIBI_LOG_DIR を優先し、未指定なら HOME/.local/share/hibi を使います。

  6. 06

    JSONに変換して、新規ファイルへ保存

    Storage → Record

    Storage.save 内でJSON化 → 保存先の準備・Git外の確認 → 排他的なファイル作成 → 書き込み・クローズの順に進みます。

    同名ファイルがあれば連番を進めます。保存中の失敗・中断では今回のファイルの削除を試みます。

  7. 07

    保存先を表示して終了する

    Storage → report

    Storage が、Main から渡された report 関数を実行。「保存しました: …」を表示・flushしてから、保存処理が成功を返します。

    表示処理が失敗した場合も、今回のファイルの削除を試みてエラーを返します。

ケースを切り替えて見る

どこまで処理が進むかを強調します。

4問を終え、1つ以上の回答があれば保存へ進みます。ファイル出力と保存先の表示が完了すると、正常終了します。

exit 0
途中で止まるときの扱い
状況処理終了コード
全問未回答保存しない旨を表示し、保存先の取得前に終了。0
Ctrl+C / SIGINT入力中なら全回答を破棄。保存中に Sys.Break を受けた場合は今回のファイルを削除して中断。削除にも失敗した場合はエラーとして終了。130
削除失敗は 1
Ctrl+D / EOFそれまでの回答も保存せず終了。パイプ入力の末尾も、改行で確定していなければ未確定の入力として扱う。1
入力・日時・保存先のエラーMain が理由を標準エラー出力へ表示して終了。入力値の検証エラーは再入力で扱う。1
保存・報告のエラーStorage が今回のファイルの削除を試み、Main がエラーを表示。削除自体の失敗も理由に含める。1

コールバックとは：別の処理から呼んでもらうために渡す関数です。ここでは Main が「保存先を表示する関数」を渡し、Storage が書き込み後に実行します。画面表示の内容は Main、実行するタイミングは Storage が決めています。

03

記録するデータ

4つの回答に開始日時を加えた、5項目の記録です。

Record.t → JSON

入力は1行ずつ、保存は1回分まとめて。

Main が4問を集め、Record.create で検証・生成した記録だけを Storage に渡します。入力中に回答を順次ファイルへ保存する仕組みはありません。

OCamlの option は「値がある／ない」を表す型です。未回答は None、JSONでは null になります。

recorded_at
質問開始時のローカル日時と時差。文字列。
score
気持ちを表す1〜5の整数、または未回答。
accomplishments
今日やれたこと。文字列、または未回答。
moments
心が動いた場面。文字列、または未回答。
next_step
明日少し変えたいこと。文字列、または未回答。
1回の実行 → 1つの .json架空の回答例
{
  "recorded_at": "2026-10-21T18:00:00+09:00",
  "score": 4,
  "accomplishments": "同僚の相談に乗った",
  "moments": "案を見せ合った → 面白かった",
  "next_step": null
}

保存先の既定値：~/.local/share/hibi/
ファイル名の例：2026-10-21T18-00-00+09-00-001.json
日時と連番で名前を決め、既存のファイルを保持します。

04

テストの位置付け

データと保存のルール、端末を含めた実行時の振る舞いを、別々のテストで確認しています。

既存の検証範囲

OCaml · データと保存

Record / Storage のルール

test/test_hibi.ml
  • スコア・空白・UTF-8の入力検証
  • 日時、JSONへの変換、未回答の扱い
  • ディレクトリ・ファイルの権限と名前の衝突
  • Git内の保存拒否、シンボリックリンク経由の判定
  • 報告失敗・キャンセル時の削除と既存記録の保持

Python · CLI全体と端末

Input と、Main から保存まで

test/terminal_input_test.py
  • 擬似端末（PTY）で日本語の行編集を再現
  • Ctrl+C・Ctrl+D・SIGINTと端末設定の復元
  • 標準出力リダイレクトの拒否、外部エディタの無効化
  • 全問未回答と、保存先が不正なときの動作
  • パイプ入力、不正スコアの再入力、改行前のEOF

OCaml / QCheck2 · プロパティベーステスト

生成と変換が守る性質

test/record_properties.ml
  • 8種類の性質を各1,000ケース検証。正常・未回答・不正入力を別々に生成
  • 保存可能な記録の制約、空白の正規化、不正スコア・UTF-8の拒否
  • Unicode・引用符・制御文字を含む回答のJSON往復と、日時・時差の保持
  • 反例を縮小して原因を絞り込み、表示されたseedで再現
Dune がまとめて実行

opam exec -- dune runtest で具体例・プロパティベース・端末入力のテストを実行します。QCheckとPythonはテスト時だけ必要です。CIではOCamlの整形・型と警告・ビルドも確認します。

コードを読む順番：まず bin/main.ml の run → collect_record → ask。そこから関心に応じて Input.read_line、Record、Storage.save をたどると、図と対応させて読めます。.mli は、外から使える型・関数を定義するファイルです。
